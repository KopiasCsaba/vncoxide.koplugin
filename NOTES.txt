NOTES.txt -- vncoxide.koplugin internals, tests and open ends
==============================================================

This file is for people reading or changing the code. The README is for users.


WHAT THIS IS
------------

An out-of-tree KOReader plugin with a VNC (RFB 3.8) **client** that renders a remote desktop
through KOReader's BlitBuffer abstraction. Pure Lua + LuaJIT FFI: no build step, no C component, nothing to compile.
The directory is `vncoxide.koplugin` and its Lua modules live in `vncoxide/`.


CODE STRUCTURE
--------------

main.lua                  Plugin entry point. Owns the settings store, registers the single
                          file-browser menu entry, keeps the session registry (one Session per
                          profile) and the app lifecycle.

vncoxide/protocol.lua    RFB 3.8 state machine: version/security handshake, ClientInit,
                          ServerInit, SetPixelFormat, SetEncodings, the server message loop, and
                          the client input messages. Transport agnostic - it never touches a
                          socket.
vncoxide/encodings.lua   Rectangle decoders: Raw, CopyRect, RRE, Hextile, TRLE, ZRLE, Tight and
                          the DesktopSize pseudo-encoding.
vncoxide/zstream.lua     Stateful zlib inflate (one stream per RFB zlib stream) - KOReader's
                          ffi/zlib.lua only offers one-shot uncompress().
vncoxide/des.lua         DES-ECB in FFI, used by VNC Authentication.
vncoxide/pxfmt.lua       The client pixel format we negotiate, plus the pixel write helpers.
vncoxide/util.lua        Byte reader/writer for protocol fields, rect unions, UTF-8 splitting.
vncoxide/keysyms.lua     KOReader key names / characters -> X11 keysyms.
vncoxide/session.lua     The transport driver: LuaSocket TCP, Wi-Fi, the poll task, tx/rx
                          buffering, attach/detach, reconnect, dirty-rect plumbing.
vncoxide/framebuffer.lua The remote plane (a TYPE_BBRGB24 BlitBuffer), the view transform
                          (fit / zoom / pan / draw) and the persistent canvas buffer that
                          holds the scaled view between draws.
vncoxide/scaler.lua      Global-coordinate sharp/smooth scaler used for partial redraws.
vncoxide/app.lua         The full-screen viewer widget: canvas, gestures (Touch and Mouse pointer
                          modes), on-screen keyboard, toolbar routing, remote input.
vncoxide/pointerfollow.lua  Mouse mode, zoomed in: one axis of the view following the pointer
                          (RustDesk's CursorModel.updatePan rule), a pure function.
vncoxide/toolbar.lua     The floating, draggable toolbar (Collapse, Display, Zoom cycle, Mode,
                          Keyboard, Rotate, Scroll up/down, Brightness, Contrast,
                          Close, More; all but the last two can be hidden), or while collapsed its
                          round button; a child of the viewer, not a window.
vncoxide/icons.lua       Absolute paths of the plugin's own icons (the icons/ folder: keyboard.svg,
                          keys.svg, zoom-1to1.svg, brightness.svg, toolbar.svg), which
                          KOReader's icon folders do not hold, and how a Button / IconButton
                          gets one.
vncoxide/contrastdialog.lua  The contrast dialog (toolbar Contrast button): a ButtonProgressWidget
                          over Settings.CONTRAST_LEVELS; the curve is applied in vncoxide/scaler.lua.
vncoxide/displaypanel.lua  The Display panel under the toolbar: zoom, scaling, orientation, picture
                          quality presets, pointer speed.
vncoxide/help.lua        The Help page text (gesture rows per pointer mode, toolbar, key strip, menu,
                          reconnect); shown in a TextViewer by ViewerApp:open_help.
vncoxide/reconnect.lua   The reconnect loop and its box (backoff, Retry now, Close).
vncoxide/menu.lua        The "More" menu (the toolbar's last button). Its rows act on a long press only on its release:
                          a release within HOLD_CONFIRM of the hold is the device's false hold
                          (InkView's late burst), i.e. a tap (VncMenu:onMenuHold).
vncoxide/keypanel.lua    The "Send keys" panel: one-shot modifier toggles and every key, for
                          any hotkey; owned by the viewer (ViewerApp:open_key_panel). Its
                          variant = "strip" is the one-row key strip above the on-screen keyboard.
vncoxide/dialogs.lua     Connection list, per-connection actions, profile editor (with its picture
                    settings).
vncoxide/keyboard.lua    KOReader's VirtualKeyboard wired to RFB key events via a stub inputbox.
                          A key's long press (its popup, Backspace's repeat) reaches the key only
                          once it lasted Keyboard.HOLD_CONFIRM (= HOLD_CONFIRM) with no lift, or moved
                          (hold_pan); lifted sooner it is InkView's late burst of a tap, and the lift
                          alone types the key (VirtualKey:onHoldReleaseKey).
vncoxide/settings.lua    LuaSettings wrapper: profiles + global settings.

tools/mock_vnc_server.py  Test fixture: an RFB 3.8 server in Python (all encodings, both security
                          types, deterministic patterns, logs every client message).
tools/proto_smoke.lua     Headless protocol tests (drives the real protocol stack over TCP).
tools/ui_smoke.lua        Headless UI tests (real plugin, dialogs and viewer widget, no KOReader
                          process, no server).
tools/vnc-server.py       PC-side launcher: shares an X11 monitor/area via x11vnc, optional red
                          on-screen frame (ctypes libX11). Standard library only.
tools/vnc_zoom.py         Its -z server: ffmpeg x11grab capture/scale/convert, RFB 3.8 (None/VNC
                          auth with pure-Python DES), ZRLE/Raw 64x64 tiles, XTest input.
tools/test_vnc_server.py  Unit + end-to-end tests for it (fake x11vnc/xrandr stubs); run with
                          `python3 tools/test_vnc_server.py` (also runs tools/test_vnc_zoom.py).
tools/tight_jpeg.b64      The fixed 32x32 JPEG the mock serves for its Tight JPEG rectangle.


DESIGN NOTES WORTH KNOWING
--------------------------

Page buttons. The device's page-turn buttons send back = Page_Up, forward = Page_Down (keys mode,
default). In wheel mode they send 3 wheel notches (button 4/5 press+release) at the last pointer
position, or the remote centre before any pointer event; the position is clamped to the current
remote size, since a DesktopSize shrink can leave it out of range.

Input priority. Decode, paint and e-ink refresh all run on KOReader's one UI thread, so a key press
that arrives while a redraw is in progress waits behind it (about 1 s on a PocketBook). Keys
themselves are always sent at once; what is held is the incremental FramebufferUpdateRequest that
normally follows each FramebufferUpdate. Once input has been quiet for Session.INPUT_QUIET (0.3 s)
the next poll sends exactly one request. Only key events and page-button wheel scrolls count as
input; taps and drags do not, and explicit full-update requests (attach, resize) are never held.
Neither do the repeats of a held on-screen Backspace (Session:send_key's is_repeat, "K ... r" to
the decode worker): one every 0.1 s renewed the 0.3 s hold, so the screen stayed still for the
whole hold and jumped at the lift; only its first Backspace holds the request, like a tap.

Protocol concurrency. protocol.lua runs as a coroutine whose transport yields ("need", n) when it
wants bytes; Session is the driver and resumes it once exactly n bytes have arrived. Everything is
therefore single-threaded and there is no blocking read anywhere. The session runs from a
UIManager:scheduleIn poll task with a per-tick byte budget and a per-tick CPU budget (30 ms), so a
large frame cannot block the UI. Exactly one FramebufferUpdateRequest is outstanding at any time,
which is what bounds memory while the viewer is closed but attached.

Visible-area requests. Zoomed in, the incremental requests ask only for what is on screen plus
Session.REQUEST_MARGIN (0.25 of the visible width/height on each side), clamped to the remote
screen: Remote:visible_remote_rect computes it, the viewer hands it to Session:set_view_area on
every paint (held during a two-finger pan/zoom until its release, or ViewerApp.VIEW_SETTLE 0.3 s
without movement), and Protocol asks its request_area provider for it. A server only sends changes
inside the requested region (libvncserver intersects with requestedRegion), so less is encoded,
sent and decoded. Whenever the whole remote screen is visible the area is the whole framebuffer and
the requests are byte-identical to before; request_full_update (attach, DesktopSize) and the
benchmark's own session stay whole-screen. Pixels outside the area go stale, so when the area moves
the bounding box of its part the previous area did not cover gets one non-incremental request. It
is written at once (the next poll tick flushes it, so a paint does no socket I/O) even though an
incremental request is outstanding: a server answers an incremental request only when something
inside it changes, so on a still screen a request queued behind it would never go out. Merging
outstanding requests is libvncserver behaviour (rfbserver.c ORs every request into
requestedRegion, which the next update answers), so there no second request is left outstanding;
other servers may differ. While requests are held for key input it waits, and then goes out
instead of the owed incremental one, as one non-incremental request of their union. While the
session is detached it is only owed: attach's whole-screen request covers it.

Detach/attach. Leaving the viewer detaches (unschedules the poll, stops reading, keeps the socket
and the plane). Re-attaching sends a non-incremental request for the whole screen, which is both
the resynchronisation and the way updates pushed while detached are absorbed. Only Disconnect
closes the socket and restores Wi-Fi, and only Wi-Fi that the plugin turned on is turned off.
KOReader's UIManager:unschedule matches by function, which is why each session schedules its own
bound `_poll_task` (one session's detach must not unschedule another's poll).
A Disconnect confirmed from the toolbar (ViewerApp:disconnect_session) then opens the connection
list; other disconnects (list actions, errors) and Leave do not.

Settings. There is no schema version. The only migration is for the released global `enable_tight`
(see "Pixel format and bandwidth" below). vncoxide/settings.lua:normalise() otherwise just keeps the
file in shape on load: missing global settings get their defaults, unknown keys are dropped,
profiles without a usable name are dropped. One invariant is enforced there too: at most one
profile may carry `autoconnect` (see below), so the first flagged one keeps it and the rest are
cleared.

Pixel format and bandwidth. These are per-connection profile fields (vncoxide/settings.lua
PROFILE_FIELDS), edited behind the connection editor's Picture button (Dialogs.picture_settings)
and stored only on Save; save_profile keeps a field the caller omits. The session reads them from
the connecting profile once per connection: `color_depth` (24, 16 or 8; vncoxide/pxfmt.lua:for_depth
gives 32 bpp RGB, RGB565 or BGR233, all expanded to the RGB24 plane), and `jpeg_quality`/`compress_level` (false or 0..9), which
Encodings.order appends as the Tight pseudo-encodings -32+q and -256+l - only when `enable_tight`
is on, since without Tight no server reads them. Servers only send Tight JPEG at 32 bpp, so JPEG
quality does nothing at 16/8-bit. normalise() resets anything else to the default (24 / false).
`enable_tight` was a released global setting: normalise() takes a stored global true as the value
of every profile without its own `enable_tight`, then drops the global (the other three never
shipped as globals and are just dropped). A change applies on the next connection only, and the
editor says so (the picture dialog's Help button, which shows PTF text in a TextViewer with the setting names in
bold and ends "Changes take effect on the next connection."; each row's long-press help is its
paragraph as plain text; and "Reconnect to apply the new settings." after saving the live
connection, only when host, port, password or one of these four changed): a live SetPixelFormat
would race updates already in flight in the old format, and the client cannot tell those apart
from the new ones. Scaling ("smooth" by default, or "sharp") is not a profile field: it is the global setting
`settings.scaling`, switched in the Display panel (Smooth / Sharp), which calls Remote:set_scaling on the live remote and repaints at once. The session
re-reads the setting (Session:_apply_scaling) whenever it creates or resizes its Remote.
VNC:save_profile still points the live session at the saved profile, and connect_profile at the
reloaded one.

Worker processes. The viewer's architecture: there is no setting and no menu switch. Every
session VNC:connect_profile creates is Session.new{ worker_processes = true } (an internal
parameter; only the picture benchmark and tests that inspect the in-process internals leave it
off), which makes the session, after the RFB handshake (also after a reconnect), fork (vncoxide/worker.lua) two processes (vncoxide/workers.lua): a decode worker, which inherits the socket
and the protocol state and decodes updates into the remote plane, and a scale worker, which scales
the visible part of the plane into the canvas. The UI process keeps the keyboard/pointer/view
logic, the e-ink refresh and the paint. Plane and canvas are MAP_SHARED memory (vncoxide/sharedmem.lua);
the pipes carry only small messages, so a big update no longer blocks the UI thread for its decode
and scale. vncoxide/renderer.lua holds the scaling the in-process path shares. Messages (the table in
vncoxide/workers.lua's header is the source):
  UI -> decode    K <keysym> <0|1>[ r] (r: a repeat); P <x> <y> <mask>; V <x> <y> <w> <h> | V -; F; N <what>;
                  T <len> + bytes (cut text); S (detached: stop reading); R (attached: resume);
                  I <n> (ping; answered at once, also while detached); Q
  decode -> UI    H <pid>; Z <w> <h> (desktop resized; the worker exits after); B (bell);
                  E <message> (error; exits after); O <n> (pong: the answer to I <n>)
  decode -> scale D <x> <y> <w> <h> [...] (plane rects fully written)
  UI -> scale     G <id> <scale> <view_x> <view_y> <cw> <ch> <btype> <dither> <mode> <contrast>
                  <invert> [<srot> <sinv>] (the view; latest wins); Q
  scale -> UI     H <pid>; C <id> full | C <id> <x> <y> <w> <h> [...] (canvas rects of view <id>);
                  E <message> (a render failed; exits after)
Physical-layout canvas: KOReader's blitFrom goes per pixel in Lua whenever the source's and the
destination's invert flags differ (night mode on PocketBook inverts Screen.bb in software) and takes
the slow rotated C blit for a rotated Screen.bb, so a full-canvas paint cost hundreds of ms on the
UI thread. When the screen buffer is of the canvas type and rotated or inverted, Remote:draw_to
sends its rotation and inversion as the optional G tail <srot> <sinv> (part of the view key and of
the canvas geometry, so a rotation or night-mode change never blits memory laid out for the old one;
the area keeps what it shows until that view's C). The scale worker renders privately and
Workers._to_physical blits (rotating, invertblitFrom for inversion) into the shared memory in the
screen's physical layout; the UI then copies it through an unrotated, uninverted view of the screen
memory at bb:getPhysicalRect(canvas), a straight row copy. An unrotated, uninverted screen and a G
without the tail take the plain layout as before; Remote.NO_NATIVE (tests) forces the old path.
Cost: in physical mode the scale worker keeps a second, private canvas (~2 MB BB8 at 1680x1264,
~8.5 MB RGB32) besides the shared one. Where KOReader's blit ignores the invert flag (its C
blitter takes every pair: Android, whose framebuffer inverts on flip, so the screen buffer holds
plain values) the tail says sinv 0 (Remote._blit_ignores_inverse). The UI's unrotated view of the
screen memory is kept on the link (link.screen_view) while the buffer's memory and layout stay.
Resize: the plane is the UI's and a worker cannot change its size, so on a new desktop size the
decode worker sends Z and exits before decoding anything of the new size; the UI then reconnects
(a fresh handshake and fresh workers). A DesktopSize of the plane's own size is no resize: the
decode worker handles it as in-process (the plane stays, a full update is requested, the view area
the UI sent is kept) and sends no Z. If the workers cannot start before the decode worker is
forked (fork or memory failure), the session carries on in-process and logs it ("worker
processes not started, decoding in-process"); a failure after that fork stops both workers and fails
the connection (Workers.start's third result; a worker may hold the socket, so the protocol state
cannot be trusted). Watchdogs (Link:poll): commands queued for the decode worker that do not move
for Workers.DECODE_STALL (2 s), or no C at all for Workers.SCALE_STALL (10 s; a full 1264x1680 render
measured 31-270 ms on emulated ARMv7) while a G is unanswered, stop the link and fail the
session ("decode/scale worker not responding"): the viewer's reconnect box, never a frozen picture.
The queued-commands check alone misses a decode worker that hangs while the user is idle (nothing
queued), so the UI also pings: after Workers.PING_AFTER (1 s) with no message at all from the
decode worker it sends one I <n> (one outstanding at a time); no message within DECODE_STALL of
the ping fails the session the same way (a hang shows the box ~3 s after the last message). Any
decode message counts as alive. A decode worker blocked writing D lines to a hung scale worker
stalls the ping too: if a G has also been unanswered for DECODE_STALL by then, the message names
the scale worker. A gap between UI ticks longer than PING_AFTER (blocked UI thread, detach,
suspend) restarts the ping's and the queue check's clocks rather than counting as silence. A
pong is no activity for the poll interval: an idle attached session costs one ping and pong per
~1 s and stays at Session.POLL_INTERVAL (pings go out only from attached ticks).
A scale worker EOF in the tick that read the decode pipe before its Z re-reads the decode pipe
once (resize, not crash). The UI polls every Workers.UI_POLL (10 ms) while a message arrived in
the last Workers.ACTIVE_FOR (0.5 s) or a G is unanswered, else every Session.POLL_INTERVAL; the
timing trace's poll gap is measured against the interval the last tick scheduled. The UI's pipe
ends are FD_CLOEXEC. What stays in-process: the fallback above when the workers cannot start; the
viewer's drawing while a session has no link (Remote:draw_to scales the plane itself, e.g. in the
resize reconnect window between the decode worker's Z and the new workers); the session and
decoder code itself, which the decode worker runs after the fork; the picture benchmark
(vncoxide/benchmark.lua creates its own sessions without the flag, so it measures one process's
decode and draw; a test asserts it).

Picture benchmark. vncoxide/benchmark.lua measures combinations (see its header); the UI is
Dialogs.picture_benchmark, behind "Find fastest picture settings" in the per-connection dialog:
intro ConfirmBox (Start/Cancel) -> a non-dismissable ButtonDialog whose title shows
"<run>/<total> (pass <p>/2): <label> — <phase>" (setTitle on every on_progress) with Cancel (bench:cancel()) ->
Dialogs.benchmark_results, a monospace TextViewer (Dialogs.benchmark_table: label line, figures
indented below so narrow screens do not wrap columns). Apply best copies the stored profile,
replaces only the four picture fields with the top scored row's and calls VNC:save_profile (a full
copy because save_profile does not keep an omitted password). Every way out returns to the
per-connection dialog. The draw canvas is VNC:benchmark_canvas: the open viewer's canvas, else the
screen in the viewer's remembered orientation without the keyboard; both fitted zoom modes are
measured as "fit". Tests inject a fake engine through Dialogs.Benchmark. The engine reports the
"tiles" phase from its next tick rather than from the session's callbacks, so a cancel() from
on_progress never disconnects a session from inside its own callback; an unexpected Lua error in a
tick, start(), the connect callback or the draw ends that combination as failed
(Benchmark:_guarded, and a pcall around the draw sink).
For the whole run the engine detaches every attached session it gets as opts.sessions (the UI
passes plugin.sessions, so the open viewer's too), so their polling, decoding and drawing do not
skew the scores, and re-attaches exactly those, with their app, when the run finishes, is
cancelled or errors (attach requests the full update that resyncs them). A combination that fails
before its handshake completes (refused, timeout, auth/security, Wi-Fi) ends the whole run:
on_done(results, connect_error), and the UI shows "Could not connect: <reason>" instead of the
table. Failures after connecting (rejected format, mid-phase error) fail only that run.
Two passes (Benchmark.PASSES): the list in order, then reversed, each run reconnecting; on the
Era (1264x1680) per-request overhead varied 0-90 ms between combinations with no pattern and the
last ones scored best, so one pass let order and Wi-Fi jitter decide the ranking. Each
combination's samples from both passes are pooled and scored by medians (Benchmark._score, pure,
unit-tested); a failure in either pass makes the row failed, "failed in pass N: <reason>" from the
first failure (shown as is, not prefixed "failed: " again). Result rows ("%.1f Mpx/s · %d ms ·
%d ms · %d KB": tile median, full-frame median, KB per full frame; the intro line names the
columns) must fit one line of the monospace TextViewer on the Era: the photo's old row, which
wrapped there, measures about 0.97 of the emulated 1264x1680 text width, so ui_smoke holds the
worst case to 0.85 of it (and checks the old row exceeds that).
The benchmark session polls every 5 ms while a request is in flight (see the vncoxide/benchmark.lua
header). It needs no changing content: every request is non-incremental (3 whole-screen ones, the first a
warm-up, then the 16 tiles of a 4x4 grid, one at a time, the held incremental request settled by
each), so the server re-encodes and re-sends identical pixels every time and every combination
gets the same pixel counts on a still screen. Each request is timed from sending (flushed at once)
until its update is decoded and drawn; the main score is the tiles' pixels per second, the closest
to everyday small updates. The "tiles" progress is reported one tick before the first tile is
requested, so the e-ink refresh of the progress title is not measured, and the draw uses the
viewer's dither flag (canvas.dither, BB8 screen plus Screen.sw_dithering).

Taps always click the remote (outside the toolbar). The plugin ignores KOReader's "activate menu on
tap" preference and shows/hides the toolbar on a swipe down in KOReader's menu zone instead; under
"tap only" the toolbar would be unreachable, and intercepting taps would put a dead spot on the
remote desktop. See ViewerApp:init_menu_zones().

The toolbar is a child of the viewer, not a window of its own (vncoxide/toolbar.lua). The viewer paints
it after the canvas and its handleEvent hands the toolbar every gesture that started on it
(ViewerApp:_toolbar_owns), so a tap on the bar never reaches the remote and the canvas around it
stays live; a window of its own would take the screen's input and hide the viewer from UIManager.
Not owned by the bar: swipes that start elsewhere (the top-zone toggle, the end of a quick drag),
a pan_release of a drag the bar did not start, multi-finger gestures (a pinch zooms wherever it is
made) and anything while a drag or long press of ours is under way (its end is ours wherever the
finger lifts).

Moving the bar: a pan that starts on it (or on its round button while collapsed) moves it, and from
then on the bar owns that drag's pans and its end (pan_release, or a swipe when the finger lifts
while still moving) wherever the finger is (Toolbar:is_dragging); a drag whose end a popup took
is over at the next pan or swipe that starts elsewhere (Toolbar:drop_lost_drag). A swipe that starts on the bar is
a quick drag of it: it is put down at the lift point (the swipe's end_pos; its pos is where it
started). While it follows the finger the old and new rectangles get "fast" refreshes, on release
one "ui" refresh over where it started and where it is. The position is stored as fractions of
the free space (toolbar_pos, Size.margin.default kept on every side), so it is re-clamped by every
relayout (rotation, resize) and keeps its relative place. While collapsed toolbar_pos is the round
button's; collapsing puts the round button at the bar's top left (where the Collapse button is),
expanding puts the bar's top left at the round button, each clamped and stored again
(Toolbar:relayout(at)). Buttons pinned to the collapsed toolbar (toolbar_pinned, only ids the full
bar shows, never Collapse or Close: Toolbar:pinned_ids) turn the round button into a short bar of the
same shape as the full one, the expand button first; with none pinned it stays the round button.
The toast (ViewerApp:show_toast) is pushed below the bar only when the bar
is where the toast would be drawn; the contrast box goes under the bar, or above it when there is
no room; the Display panel's anchor is the bar's rectangle (MovableContainer pops it down, or up).

Long press on a button: a one-line tooltip (Toolbar.TIPS) and nothing else. KOReader closes a
toast on any input that passes it, and the hold's own hold_release would close it the moment the
finger lifts, so the tooltip's toast lets hold_release and hold_pan through without closing.

Click and type, two ways (ViewerApp:_click_and_type: end a stale
action, then the armed modifiers + move/press/release, then set_keyboard_visible(true) unless the
keyboard is already wished or the Send keys panel is up; it is the button's own saved wish,
keyboard_shown):
- A one-finger drag (pan... pan_release, or a swipe) that starts on the Keyboard button
  (Toolbar:button_rect, computed from the layout, so it works before a paint; the collapsed short
  bar too) drags a keyboard icon (Toolbar.drag_icon, painted by Toolbar:paintTo after the bar;
  "fast" over old+new icon rects per move, "ui" over the last one on release) instead of the bar.
  Nothing is sent meanwhile. The drop (pan_release pos, or a swipe's end_pos) goes to
  ViewerApp:drop_keyboard_at: on the canvas and not on the bar, nor below
  dimen.h - _bottom_cover_height() (keyboard + strip, or the panel), with no popup above
  (_input_target) -> click there (Mouse mode: the pointer moves there, _mouse_x/_mouse_y follow);
  otherwise nothing. A flick without pans shows no icon and drops at its end. The keyboard keys do
  not take the pan_release/swipe of such a drop (checked), so the icon never stays behind.
- A two-finger long press: onTwoFingerHold remembers it (_two_hold, pos = GestureDetector's
  midpoint of the two contacts, time) when no one-finger action of ours is under way, under no
  popup and on the canvas spot as above; two_finger_hold_pan voids it (its pan_release then does
  nothing); two_finger_hold_release clicks (Touch at the midpoint, Mouse at the pointer) and shows
  the keyboard - unless it comes less than HOLD_CONFIRM after the hold: InkView's late burst of a
  two-finger tap, so it does onTwoFingerTap (fit) instead. A two_finger_hold that ends a long press
  or drag of ours (_two_finger_ends_ours) leaves _two_hold void, so that gesture's lift sends nothing.

Which buttons the bar shows is `toolbar_buttons` ({ id = bool }, Settings.TOOLBAR_BUTTONS has the
ids and defaults; Close and More are not in it and always shown). It replaced three switches:
Settings:normalise turns `toolbar_scroll_buttons` (both scroll ids), `toolbar_brightness_button`
and `toolbar_contrast_button` into it once, only when there is no `toolbar_buttons` yet; the old
keys are then dropped. Switching the Collapse button off while collapsed opens the bar first.
The bar only ever asks for partial refreshes of its own rectangle ("ui"; "fast" while it is dragged). The Display panel is a
ButtonDialog anchored under the bar, rebuilt in place after each choice so the check marks show the
live state; only a rotation closes it. Quality presets (Settings.QUALITY_PRESETS) are sets of the
four picture fields of the profile; Settings.preset_of() names the match or "custom".

Pointer modes (Settings: profile field pointer_mode, "touch", "mouse" or "hybrid"; pointer_speed in the global
settings, Settings.POINTER_SPEEDS 0.75 / 1.25 / 2.0). Touch mode acts at the finger. In Mouse mode the
viewer keeps a remote pointer position, a one-finger drag moves it by the drag delta taken through
the zoom and times the speed, and a tap clicks at the pointer at once (two quick taps are a double click; the armed modifiers go
with the click). A drag only moves the pointer, even right after a tap. A long press waits for its
lift (a right click at the pointer) or its first move (a left-button drag from the pointer, moved
through _mouse_move). Everything is built from GestureDetector's tap / hold / pan, no raw touch
handling. Touch mode clicks are as immediate. Hybrid mode ("hybrid"): taps and long presses as in Touch mode,
a one-finger drag never presses a button but scrolls (_hybrid_pan_move -> _scroll_by_drag, at where the drag
began). The step is in remote pixels: one wheel notch per hybrid_notch_px (a profile field, default 240,
10..1000, the viewer menu's "Hybrid scroll distance") of finger movement divided by the zoom
(Remote:get_scale()), so the content follows the finger at any zoom; what one notch really scrolls is
the remote OS's / application's choice (desktop browsers: about 3 lines, some 50-120 px), hence the
setting. An earlier step of a fixed fraction of the reader screen (1/30, then 1/15) moved the content
by a zoom-dependent amount, about 4x the finger's distance on the device.

Physical keyboard. Printable characters arrive as TextInput events, not as key events, and
SDL 3 only delivers those after Device:startTextInput() ("Text input events are not received by
default", SDL_keyboard.h). KOReader's own callers are its text fields, so the viewer calls
Device:startTextInput() while it is shown (ViewerApp:_ensure_text_input), re-asserts it after one
of its own dialogs (an InputText pairs startTextInput with stopTextInput) and calls
Device:stopTextInput() when it closes. Named keys go out as X11 keysyms; only the Menu key is kept
back (it toggles the in-app menu), and Back leaves the viewer only on devices without a keyboard.
KOReader's Input never reports Ctrl, Shift or Alt as keys (only as the next key's `modifiers`), and
SDL types no text for Ctrl/Alt+letter: ViewerApp:onKeyPress sends the held ones around a named key,
and a Ctrl/Alt+printable key itself (its text event, if any, is dropped); the release lets go of
exactly what the press sent (checked against x11vnc with real SDL key events from xdotool).

Keyboard placement and zoom. The canvas (ViewerApp:_layout) is the whole widget, except when the
whole remote screen at the current zoom fits in the space the visible on-screen keyboard leaves -
then the canvas is that space, so the view is placed above the keyboard rather than behind it. The
zoom is never changed by that; only the placement. "Fit (with keyboard)" is the mode that fits the
space the keyboard leaves (and therefore follows the keyboard); "Fit screen" fills the screen and
fixed ratios are absolute. Remote:set_canvas() keeps the view's own idea of its space in step,
which matters because set_scale()/zoom_at() clamp and centre against it.

Send keys panel (vncoxide/keypanel.lua). A bottom-anchored, non-modal widget above the viewer that the
viewer treats as part of itself, like its keyboard (ViewerApp:_is_overlay): canvas taps still reach
the remote, remote updates keep repainting under it, and the canvas places a view that fits above
it, exactly as for the keyboard (ViewerApp:_bottom_cover_height; the keyboard hides while it is
open). The panel swallows gestures on its own rectangle that none of its buttons took, so the gaps
between buttons never click the hidden remote; a drag belongs to where it started. Its height never
changes with the tab (every grid is three key rows tall), so switching tabs never moves the view.
Its top row is the key strip's row (KeyPanel:_top_row), only the two buttons at the left differ
(panel: close, keyboard; strip: close, Send keys); "Modifiers only" on the Keys tab sends the armed
modifiers alone.
The Hotkeys tab's buttons are fixed combos sent through KeyPanel:replay (exactly as named, armed
modifiers cleared, remembered in the recent row); the menu's Lock screen entry moved there (Super+L).
Modifiers are armed by a tap and used by exactly one action, then disarmed; nothing stays down
between actions. A panel key: armed modifier downs in Ctrl, Shift, Alt, Super order, key down, key
up, ups in reverse. A canvas tap, long press or drag: ViewerApp:_press_armed takes them from the
panel and sends the downs before the pointer press; _release_action_mods sends the ups after the
pointer release (for a drag, at its PanRelease). A drag cut short by the panel closing
(ViewerApp:close_key_panel) or the viewer closing (ViewerApp:onCloseWidget, which leave_app and
disconnect_session both reach before the session is detached or torn down) gets its ups there.
A drag or long press belongs to where it started (KeyPanel:_gesture_owner): one begun on the
canvas keeps its hold_pan / pan_release / hold_release even when the finger lifts over the panel,
and the viewer takes those releases anywhere on the screen, acting only on a press it sent itself
(_drag_active, _hold_active), also with a popup on top by then. A one-finger drag or long press
that gains a second finger becomes a two-finger gesture in GestureDetector (Contact:handlePan with
a buddy contact) and ends in two_finger_pan_release, never in pan_release; every two-finger handler
therefore first ends such an action (ViewerApp:_end_pointer_action: button up, then the modifiers).
A quick two-finger drag (two_finger_swipe) only ends the view pan. A two-finger drag always pans
the view (there is no scroll lock). Wheel notches come from the Hybrid mode's one-finger drag (_scroll_by_drag, at
_wheel_position), the toolbar's optional scroll buttons (ViewerApp:scroll_wheel) and the page buttons, and are not modifier actions. A drag or hold whose release was eaten by the keyboard or menu is ended by the next
tap/pan start/hold, any send_key, or showing the on-screen keyboard (_end_stale_pointer_action).
Gestures off the panel never reach its buttons (KeyPanel:handleEvent): a button rebuilt since the
last paint does not know its place yet. Replaying a recent combo is an action too: it clears the
armed modifiers rather than adding them. The release of the Back key that closed the panel is not
forwarded (its press never was).
Recent combos live in the `recent_combos` setting, validated on load: known modifiers once each in
press order, keysyms within 0..0x1FFFFFFF, no duplicates (whatever order their modifiers were
listed in), at most four.

The on-screen keyboard yields to popups. KOReader stacks a non-modal Menu *below* the modal
VirtualKeyboard, so the keyboard would cover a menu's lower half; ViewerApp:evaluate_keyboard()
therefore only shows it while the framebuffer view owns the screen. Popups the plugin opens notify
the viewer directly. Anything else cannot be noticed by repainting - UIManager:_repaint starts at
the topmost full-screen widget, so a widget appearing *above* the viewer never repaints it - hence
the 250 ms re-check (_watch_keyboard_state). That is also why a toast (a Bell notification) is
explicitly flagged `toast = true`: it is allowed to share the screen with the keyboard.

The keyboard has no gestures of its own any more: the toolbar's Keyboard button shows and hides it
together with the key strip (tap); dragged out onto the remote it clicks there and shows it (above). KOReader's keyboard consumes swipes itself
- every VirtualKey carries a SwipeKey ges_event over its own rectangle whose handler always returns
true and runs the key's swipe_callback (a south swipe on `q` inserts its variant) - and
WidgetContainer:handleEvent propagates to the children first, so a "swipe down on the keyboard to
put it away" would mean overriding the keys' own gesture handling. Deliberately not done; that is
why the earlier swipe-up/swipe-down keyboard zones are gone. The viewer is registered
`is_always_active` (c.f. ViewerApp's prototype): UIManager:sendEvent offers a gesture to the
topmost widget first and then to the always-active ones, so canvas gestures keep working
underneath the on-screen keyboard (`_input_target()` ignores the viewer's own keyboard).

The key strip (KeyPanel with variant = "strip") sits on top of the on-screen keyboard, bottom_offset
pixels above the screen bottom (the keyboard's height, kept in step by KeyPanel:set_bottom_offset).
Its modifiers arm and are taken like the panel's; what it sends is not added to recent_combos, and
while a modifier is armed the viewer hands it the on-screen keyboard's keys too
(ViewerApp:send_osk_key). It has no Release all and no Back/Menu handling: it is part of the keyboard.

The keyboard's wish (ViewerApp.vk_wanted) is saved as `keyboard_shown` whenever the user changes it
(ViewerApp:_set_keyboard_wish: the toolbar button, the strip's close, the panel's keyboard icon and
its close), and the viewer starts from it; popups that hide the keyboard and leaving the viewer do
not touch it. It replaced the `keyboard_always_visible` menu switch: Settings:normalise turns an old
`keyboard_always_visible = true` into `keyboard_shown = true` once, the old key is then dropped.

Long-press popups of the on-screen keyboard's keys (accented letters) are KOReader's VirtualKeyPopup.
Its centre key, the plain letter, reuses the parent key's callback, which closes only its
close_after_callback_widget - nil on a key of the main keyboard - so picking the plain letter typed
it and left the popup on top. Keyboard.new therefore checks, after every key it sends, on the next
tick, whether a popup of its keyboard is still on the window stack and closes it (its onCloseWidget
refreshes its own area, "ui"); the popup's other keys have closed it by then themselves, so it is
never closed twice.

A swipe reaches the viewer *after* the pans that led up to it and *instead of* a pan_release
(`Contact:panState`), so a quick drag ends as a swipe: ViewerApp:onSwipe lets go of the button and
the modifiers at the last pointer position, and the top-zone toolbar swipe ends the drag itself
too. Withholding the press until a gesture is known not to be a swipe would delay every canvas drag.

Reconnect (vncoxide/reconnect.lua). ViewerApp:on_session_error opens a box over the last picture
(ButtonDialog: Retry now, Close; Back = Close) and retries with Reconnect.BACKOFF 2, 4, 8, 15, then
30 s forever; every attempt is Session:connect on the same session, which keeps the app and the
plane, and there is one loop per session. The loop lives with the open viewer only: a session that
drops while the viewer is closed stays in "error" (the toast), and reopening the viewer
(ViewerApp:onShow) shows the box with no automatic retries until Retry. Leaving the viewer stops the
loop and cancels its timer; ViewerApp:onResume retries at once when the loop is running. Keep-Wi-Fi
mode (Session:set_keep_wifi): Session:_fail and Session:hangup normally restore Wi-Fi when this
plugin turned it on, so a retry loop would turn it off and on again for every attempt; while
keep_wifi is on they leave it up, and the duty to turn it off stays with the session. Turning it off
with no connection restores Wi-Fi; the last connection to end still turns it off. A quality preset
change uses the same box ("Reconnecting...") through Session:hangup plus a connect with the new
picture fields, and writes them to the stored profile only after that connect succeeds.

Refreshes, and why a full-screen widget has to ask for them. UIManager:show/close only queue the
refresh the *caller* passed; with no refreshtype they queue nothing at all (`_refresh(nil, ...)`
returns), and the widgets they uncover are merely flagged for repaint. On an LCD that is
invisible - a repaint is the screen - but an e-ink panel only changes where a refresh asked it to,
which is what made the viewer (a full-screen InputContainer that owns a live image) render in
bands, keep the desktop where a menu should be, and leave the file browser off the panel after a
disconnect. The viewer is therefore shown and closed with an explicit `"full"` (main.lua),
onShow() asks for `"full"`, onCloseWidget() ends with `UIManager:setDirty(nil, "flashui")` (a nil
widget and no region mean the whole screen, and it merges with - and dominates - any regional
request queued in the same tick), and every wholesale change (a new connection, a remote resize, a
zoom, the keyboard appearing, a menu opening) goes through ViewerApp:_wholesale_change(): a
full-screen flash, plus `_needs_flash` so the *next* remote frame - the first one carrying the new
geometry's content - is flashed rather than blitted rectangle by rectangle.

Two traps are worth remembering, both verified against core. UIManager:_repaint *does* have a
safety net - if a widget was painted and nothing was queued, it enqueues one full-screen
`"partial"` - but it is skipped whenever *any* refresh is already in the queue; the on-screen
keyboard closing on its own (VirtualKeyboard:onCloseWidget) queues a refresh of just its own area,
and that regional request was enough to leave the freshly painted home screen unpushed (measured:
60 % of the screen; 75 % with a VNC rectangle pending at the same moment). And KOReader's
promotion counter (FULL_REFRESH_COUNT, c.f. UIManager:_refresh) only ever promotes `"partial"`, so
a viewer that refreshes its rectangles with `"ui"` never gets a periodic flash however long it
runs - hence the explicit flush above. `"partial"` itself is deliberately *not* used for the
rectangles: on a REAGL Kindle it is the REAGL waveform, i.e. a flash per rectangle, which is why
ImageViewer uses `"ui"` for the same job.

Platform. Nothing in the plugin is SDL specific: the only input-platform calls are
Device:startTextInput/stopTextInput, and Device:isTouchDevice()/hasKeyboard() are asked rather than
assumed. The single external interface in the whole plugin is zlib: zstream.lua declares z_stream
and inflate*/deflate* and loads the library with ffi.loadlib("z", 1) - the exact call core's
ffi/zlib.lua makes, so the monolibtic redirects (Android, iOS) apply. It deliberately declares only
what ffi/zlib_h.lua does not (that one has compressBound/compress2/crc32/uncompress). DES is
hand-rolled FFI, so there is no libcrypto/OpenSSL dependency, and LuaSocket is used for raw TCP
only (no TLS, so LuaSec is not needed).

The "connect at start" is a per-profile `autoconnect` flag, deferred to the next UI loop turn
(`VNC:schedule_autoconnect` -> `UIManager:nextTick` -> `VNC:autoconnect_at_boot`, scheduled once
from init()). Only one profile may carry it: `Settings:save_profile` and `Settings:set_autoconnect`
clear it on every other profile when it is set, and `Settings:normalise()` keeps the first flagged
profile and clears the rest on load, so the invariant holds for a hand-edited file too. A failed
boot connect reports itself through `connect_profile` - the same "Could not connect to ..." message
a manual attempt shows - and leaves the normal UI in place; there is no retry. If `start_with`
still names us but no profile is flagged, the boot does nothing and logs a warning.

"Start with". KOReader builds that submenu from a hard-coded list of five values and has no boot
hook and no registry for it: reader.lua's if/elseif chain knows only its own values, and an unknown
one silently opens the file manager. A plugin can still get an entry in, through the generic
`sorting_hint` orphan mechanism - an item carrying `sorting_hint = "start_with"` is nested by
MenuSorter into the submenu whose id is `start_with` (ui/elements/filemanager_menu_order.lua).
Presence has to follow the flag *after* the menu is built (the file-manager menu is cached), so a
`sub_item_table_func` filters the entry out when nothing is flagged - it is absent, not disabled -
and the core label function is wrapped additively, because core's `text_func` falls through
(returning no value) for a value it does not know and would leave "Start with" with nothing after
it. (TouchMenu resolves that
function; the legacy non-touch `Menu` path reads the static table the sorter filled, so there the
entry is unconditional - that path is only for a device with neither touch nor a d-pad.) The
choice itself is stored as `start_with = "vncoxide_autoconnect"`. Core's boot branch cannot be
intercepted (external plugins are not loaded before FileManager:init), so selecting the entry makes
KOReader open the file manager first and the deferred autoconnect then shows the viewer over it;
that first frame is inherent to doing this without shipping a userpatch. With nothing flagged the
entry is absent, and a stale `start_with` is only logged.

KOReader internals relied on (could change under us): UIManager._window_stack (for "is a popup
above us"), UIManager:scheduleIn/unschedule/nextTick/setDirty, VirtualKeyboard's inputbox protocol
and its showKeyboard/hideKeyboard/setVisibility, Screen:getSize/setRotationMode, the
SetRotationMode/ScreenResize events, DataStorage/LuaSettings, and NetworkMgr. Tools and gestures
use the documented InputContainer APIs (registerTouchZones/updateTouchZonesOnScreenResize,
ges_events with function ranges so they follow rotation without re-registration).

On e-ink the widget colour type may be BB8: the plane is always RGB24, cross-format blits go
through BlitBuffer, and the grey path uses ditherblitFrom when Screen.sw_dithering is on.

Drawing: Remote keeps the scaled view in one persistent canvas-sized buffer (`_canvas_bb`, of the
screen buffer's type: BB8, RGB24 or RGB32; any other type gets RGB24), reallocated only when the
canvas size or that type changes. The session calls `Remote:mark_dirty(x, y, w, h)` per decoded
rect; `draw_to` rescales (vncoxide/scaler.lua) only `Scaler.dst_rect_for` of those rects, merged, and
recomputes the whole buffer after a pan/zoom, a canvas resize, a scaling-mode change
(`Remote:set_scaling`), a plane resize or `mark_dirty()` without arguments. Every paint then blits
the whole buffer, so a popup closing or the keyboard going away needs no special handling: only the
scaling is partial. With sw_dithering on, the canvas is dithered into a second persistent buffer
(`_dither_bb`) only where it was recomputed, and that buffer is what gets blitted: KOReader's
ordered dither is indexed by the source position, so this is exactly the whole canvas dithered
(desktop, 1264x1680 BB8: a small update's paint went from ~4 ms, a full-canvas ditherblitFrom, to
under 0.1 ms). Into BB8 the smooth downscale (box filter) averages grey values, i.e. it is the
floored grey of the exact colour mean. At scale 1 the view offset is rounded to a
whole pixel so the canvas is a plain copy of the plane. Taps map the canvas pixel's centre
(`floor(view + (c + 0.5) / scale)`), which is the remote pixel the sharp mode draws there.

Decoder hot path (LuaJIT): no per-pixel or per-field strings, closures or tables. The protocol
reader's fixed-size reads and `ptr(n)` take a pointer straight into the session's receive buffer
(`io.read_ptr` / `Session:_read_ptr`) instead of a `rx:sub` string each; ZRLE's RLE tiles are read
through a local pointer/position into the inflated buffer, and runs are filled in bulk (memset when
grey, doubling copies when long). Measured with recorded x11vnc streams replayed offline: Hextile
24-bit 14.0 -> 7.6 ms/frame, ZRLE 16-bit 24 -> 12 ms, ZRLE 8-bit 8.7 -> 3.1 ms (1264x1680); what
is left of ZRLE/Tight is mostly zlib itself. One trap seen while doing this: LuaJIT miscompiled
`ffi.cast(ptr_type, s) + off` when `s` was a constant (immutable upvalue) string - the load used
the bare offset as the address and crashed. Keep such strings in a table field (as `self.rx` is).

Compressed payloads are not copied either: ZRLE's and Tight's zlib data and Tight's JPEG go to zlib
(`ZStream:inflate_ptr(ptr, len, limit)`) and TurboJPEG as pointer + length from `reader:ptr(n)`.
That pointer is only valid until the reader's next read, and the session may move its receive
buffer between pump steps, so each decoder uses it up in the same call that took it (inflate and
tj3Decompress8 neither read nor yield) and decodes the tiles from the stream's own output buffer.


TIMING TRACE (finding out where a lag goes)
-------------------------------------------

Every line starts with "vnc-timing:" and goes through logger.dbg, so it exists only while KOReader's
debug logging is on (Util.timing_enabled() reads dbg.is_on live; off = one field read per event, no
formatting). Enable: Settings (gear) -> Developer options -> Enable debug logging. Reproduce, then take koreader/crash.log (the "koreader" folder on the
device: it is where KOReader writes its log). Filter with: grep 'vnc-timing' crash.log

  vnc-timing: input key|wheel           a key / wheel press was noted (Session:note_input)
  vnc-timing: update rects=N bytes=B decode_ms=D wall_ms=W
        one FramebufferUpdate. decode_ms = CPU time summed over all poll ticks that worked on it;
        wall_ms = first byte -> on_update_done. wall >> decode means it was spread over many ticks
        or the UI thread was busy elsewhere.
  vnc-timing: paint ms=P canvas=WxH scale=S mode=smooth|sharp recomputed_px=N [blit_ms=B]
        one ViewerApp:paintTo (rescale of the changed areas into the canvas buffer, then its blit
        into the screen buffer). recomputed_px = canvas pixels rescaled (W*H after a pan/zoom, 0
        when nothing changed); blit_ms, only when dithering, is the dithered blit's share of P.
  vnc-timing: poll gap ms=G             the previous _poll was more than 2 x POLL_INTERVAL (100 ms)
        ago: the UI thread was blocked in between, e.g. in the e-ink refresh. Not logged right
        after attach.

Reading it: after an "input" line, a large "poll gap" means a blocking refresh delayed the next
event; a large "paint" means our blit is slow; a large decode_ms means decoding hogs the thread.
Lines carry KOReader's own timestamps, which is how they correlate with each other.


TESTS
-----

Protocol layer (needs python3 with the standard library, libcrypto with the legacy provider for the
mock's DES, and KOReader's own LuaJIT):

    PLUGIN=~/.config/koreader/plugins/vncoxide.koplugin
    cd /usr/lib/koreader && \
      LUA_PATH="$PLUGIN/?.lua;./common/?.lua;./common/?/init.lua;;" \
      LUA_CPATH="./common/?.so;;" \
      ./luajit "$PLUGIN/tools/proto_smoke.lua" --tmp /tmp/vncv_smoke

It starts one mock_vnc_server.py per case on an ephemeral port and drives the real protocol stack
over a real socket: DES against FIPS vectors, the VNC-auth bit reversal, the pixel format and
encoding list as they hit the wire, None/VNC security (including a wrong password), every encoding
decoded pixel-exactly, ZRLE stream continuity across many rectangles, DesktopSize, the exact bytes
of pointer/key/cut-text messages, and the fatal path for an encoding we never advertised. The mock
verifies VNC Authentication with OpenSSL's DES (through ctypes), i.e. with an implementation

UI plumbing (headless, no KOReader process, no server):

    PLUGIN=~/.config/koreader/plugins/vncoxide.koplugin

      rm -rf /tmp/vncv_ui_home && KO_HOME=/tmp/vncv_ui_home \

      ./luajit "$PLUGIN/tools/ui_smoke.lua"

The ui suite is not idempotent: a reused KO_HOME keeps the "fresh profile" settings of an earlier run
and fails two checks, so it needs a fresh (wiped) KO_HOME every time.

It builds the real plugin, its dialogs and a real viewer widget against KOReader's widget stack and
checks the flows that are hard to reach by hand: every menu/dialog returns to where it came from,
a failed connection returns to the connection list with exactly one dismissable message, the
canvas follows rotations, the keyboard neither rescales nor moves a view that does not fit above
it, the fitted zoom modes and the keyboard-aware placement behave, the keyboard yields to popups,
the toolbar (its buttons, their tooltips, collapsing, dragging and clamping, the top-zone swipe
toggling it, taps on it never reaching the remote, the Toolbar buttons… menu), both
pointer modes' gestures (the instant Mouse click, long press then drag, two-finger tap, no scroll or
rotate gesture, click and type by the Keyboard button's drag and by a two-finger long press), the Help page and the mode tooltip, the two-finger drag always panning, the Display panel and its quality presets, the More menu, the key
strip, the reconnect box and loop (backoff, Retry now, Close, no background retry, Wi-Fi kept on while
retrying), platform text input is enabled exactly while the viewer is shown, typed
text and physical keys reach the remote (through KOReader's own SDL event handler), the Send keys
panel's combos, one-shot modifiers on keys and canvas actions, recent list, close paths and per-tab
keysyms behave (with taps on its buttons delivered through the real widget stack), and the settings
store survives a hand-edited or empty file. The
`autoconnect` flag round-trips through the file, survives an edit that does not mention it, clears
any other flagged profile (and a hand-edited file with two is normalised to the first on load), the
actions dialog's switch and the list's marker work, the deferred tick connects the flagged profile
(and nothing when none is flagged, with the network stubbed), a failed boot connect is reported
like a manual one, and the **VNC auto connect** entry is nested into KOReader's **Start with**
submenu by the real MenuSorter only while a profile is flagged (and the stale-setting fallback is
logged). The viewer checks at the end model the *panel*
as well: an e-ink panel is a medium that only changes where a refresh asked it to, so a screen
buffer that was painted but never refreshed is caught as stale pixels (that is the check the
missing `"full"`/`"flashui"` on show/close and the missing flash on a wholesale change used to
fail, with 60 % of the screen left over in the close case). `KO_HOME` is needed because KOReader's
widget cache lives under it.

Live end-to-end (GUI): run the mock, run KOReader, drive the plugin through KOReader's HTTP
inspector (port 8989, httpinspector.autostart = true):

    PLUGIN=~/.config/koreader/plugins/vncoxide.koplugin

Inspector grammar: a trailing "/" calls a method (arguments are simple values - a string "0" stays

WHAT HAS BEEN VERIFIED, AND WHAT HAS NOT
----------------------------------------

Verified on a desktop with the SDL Emulator device, against tools/mock_vnc_server.py:
all seven encodings rendering in the live GUI; pointer, key and text input reaching the server;
the on-screen keyboard overlapping without rescaling, following rotations, yielding to menus and
dialogs, and a view that fits being placed above it; the zoom modes (fit screen / fit with
keyboard / fixed ratios) including their menu labels; detach/keep-alive/reconnect; the Wi-Fi
auto-connect/restore semantics; the grey-screen (BB8) dithering path; and the connection dialogs'
back-flows.

Not verified, and where to look first if something is wrong:

- The gesture *detector*: multi-touch gestures (pinch/spread/two-finger drag/two-finger tap) cannot be
  synthesised on this box (no ydotool/wtype, /dev/uinput is not writable, no bare X server, and
  Xwayland ignores XTest keys for an unfocused window), so the handlers are tested but the wiring
  from real fingers is not. Same for a real swipe in the toolbar zone and for the Mouse-mode long press then drag timing.
- Tight compression: exercised against the mock only. It is not RFC 6143 and servers differ in how
  they read its control byte (0x0A is "uncompressed" in libvncclient, "PNG" in TurboVNC/noVNC);
  the implementation follows libvncclient, cross-checked against noVNC. Flip the profile
  ["enable_tight"] default only after a real server has been verified.
- 16/8-bit decoding and the Tight quality/compression pseudo-encodings: checked only against
  tools/mock_vnc_server.py, whose 16/8-bit Tight gradient encoder was written together with the
  decoder. Test against a real x11vnc at 16-bit with Tight on first.
- Page-button wheel mode: covered by the headless UI tests only.
- tools/vnc-server.py frame drawing: checked under Xvfb only (border position, removal on close).
  Opacity is untested because it needs a compositor.
- Real e-ink hardware: the BB8/rotation/NetworkMgr paths exist and are exercised in their emulated
  forms only. The emulator cannot show the *effect of a refresh kind* at all - every mode falls
  through to the same refresh implementation there - so "the panel receives a full-screen, flashing
  refresh whenever the whole canvas changes" is asserted by the panel model in ui_smoke.lua, while
  how a given Kindle's EPDC renders that refresh (a partial waveform mishandling a wholesale change
  is what the flicker and the ghosted strips looked like) still needs the device.
- Nothing from the visible-area / forced-benchmark / stay-open-menu round has run on the e-reader
  yet: visible-area requests against a real server and panel, the menu staying open, and the
  benchmark's 5 ms poll and tile scoring. The benchmark was run headless against a real x11vnc only.
- Suspend: while KOReader is suspended the poll task simply does not run and the single
  outstanding update request is buffered by the kernel. A connection that dies across suspend
  shows the reconnect box; the retry on resume (ViewerApp:onResume) only applies while that loop is
  running. Re-requesting a full update on resume for a connection that survived is not implemented.
- TLS/VeNCrypt/SASL servers, and security types other than None/VNC Authentication: unsupported by
  design (the handshake reports them as unsupported).
